# Spec: Task notes and completion log

## Summary

Make task work history real without taking on the full Work Area merge. A task
gets an append-only notes/activity thread backed by `TaskUpdate`, and completing
a task from focus records a typed completion event in that same thread while
preserving the existing `Task.completedAt` field used by Today and Review.

This is the focused slice extracted from `work-area-merged.md`: notes plus
completion logging only. Route merging, Not Doing, task archive, and Logbook
restore are explicitly out of scope.

## Why

`TaskUpdate` already exists in the schema as "activity log / progress notes,"
and `getTask` already includes `updates`, but no operation creates a note and no
UI renders the thread. Focus mode is also too thin: it shows the task and a
Done button, but it does not let the user write down progress or leave a durable
record of how the task finished.

At the same time, the app already has the right durable completion field:
`Task.completedAt`. `getDoneToday` and future Review surfaces depend on it. The
new completion log must add context, not replace that source of truth.

This feature makes completion auditable:

- User-authored notes are appended to the task thread.
- System events are appended to the same thread.
- Completing a task writes both `Task.completedAt` and
  `TaskUpdate(kind=COMPLETED)`.

## Scope

Build only this slice:

1. Add a `kind` discriminator to `TaskUpdate`.
2. Add an operation to append user-authored task notes.
3. Render the task's notes/activity thread in Focus mode.
4. Change the focus Complete action so it marks the task done and writes a
   `COMPLETED` activity event.
5. Keep existing list/detail read paths working.

## Data Model

### `TaskUpdate.kind`

Add an enum and field:

```prisma
enum TaskUpdateKind {
  NOTE
  COMPLETED
}

model TaskUpdate {
  id        String         @id @default(uuid())
  body      String
  createdAt DateTime       @default(now())
  kind      TaskUpdateKind @default(NOTE)

  task   Task   @relation(fields: [taskId], references: [id], onDelete: Cascade)
  taskId String

  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  userId String
}
```

Only `NOTE` and `COMPLETED` are required for this feature. Do not add
`STARTED`, `PAUSED`, or `NOT_DOING` here; those belong to the broader
`work-area-merged` follow-up.

### Completion Source Of Truth

`Task.completedAt` remains the source of truth for completion time. The
`COMPLETED` update is an activity-log record for display and context.

When a task is completed from focus:

- `Task.isDone = true`
- `Task.completedAt = now`
- `Task.startedAt = null`
- append `TaskUpdate(kind=COMPLETED, body="Completed")`

The exact display copy can be generated by the UI from `kind`; the stored body
may stay plain and stable.

## Server Operations

### `addTaskUpdate`

Add an action:

```ts
addTaskUpdate({ taskId, body })
```

Behavior:

- Requires auth.
- Finds the task by `id` and `userId`.
- Trims `body`.
- Rejects empty notes.
- Creates `TaskUpdate` with `kind: "NOTE"`.
- Returns the created update.
- Does not mutate task status, `startedAt`, `completedAt`, priority, size, or
  any filing fields.

### `completeTaskFromFocus`

Add an action:

```ts
completeTaskFromFocus({ taskId })
```

Behavior:

- Requires auth.
- Finds the task by `id` and `userId`.
- Rejects missing tasks with the existing "Task not found." style.
- If the task is already done, returns the current completed task without
  creating another `COMPLETED` event. Double-clicking Complete must be
  idempotent.
- Requires `startedAt != null`. This keeps the product rule: completion happens
  from focus, after Start.
- In one transaction:
  - updates the task to `isDone=true`, `completedAt=now`, `startedAt=null`
  - creates exactly one `TaskUpdate(kind=COMPLETED, body="Completed")`
- Returns a small result containing the task id and completion timestamp.

Do not change `toggleTaskDone` in this slice unless it is necessary to route
Focus mode through `completeTaskFromFocus`. Existing list completion behavior
may remain until `work-area-merged` removes completion circles.

## UI

### Focus Mode

Update `FocusMode` so the user can see and append work notes while focused.

Required elements:

- Task title and existing metadata remain.
- Existing `task.content` still renders as durable task notes/body.
- Below the content, render an activity thread from `task.updates`.
- Render `NOTE` entries as user-authored notes with body and timestamp.
- Render `COMPLETED` entries as a muted system row such as `Completed · 9:41 AM`.
- Empty thread copy: `No notes yet.`
- A compact note composer sits near the thread.
- `Enter` in the composer posts the note.
- `Shift+Enter` inserts a newline if the composer is multiline.
- `Esc` keeps its current focus-exit behavior when the composer does not own
  the event.
- The Complete button calls `completeTaskFromFocus`, not `toggleTaskDone`.

The UI should stay quiet. This is a working surface, not a comments product.

### Data Shape

The page or parent that opens Focus mode must pass updates into `FocusMode`.
If the current focused task source does not include updates, fetch the task
detail with `getTask` before or inside focus. Prefer the smallest change that
keeps Focus mode reliable.

Sort updates oldest-to-newest in the thread. Prefer changing `getTask` to return
updates in ascending `createdAt` order so every consumer gets chronological
activity by default.

### Task Detail

Task detail may render the same activity thread if it is cheap to reuse the
component, but it is not required for this slice. The required surface is Focus
mode.

## Cache Invalidation

After `addTaskUpdate`:

- Invalidate/refetch `getTask` for the task.

After `completeTaskFromFocus`:

- Invalidate/refetch `getTask`.
- Invalidate/refetch `getTopTask`.
- Invalidate/refetch `getTasks`.
- Invalidate/refetch `getDoneToday`.
- Invalidate/refetch `getAppData` if inbox/task counts or shell data depend on
  completed/open task counts.

Use the existing query-client patterns already present in the app.

## Done Conditions

### Schema

- [ ] `TaskUpdateKind` enum exists with `NOTE` and `COMPLETED`.
- [ ] `TaskUpdate.kind` exists with default `NOTE`.
- [ ] Migration runs cleanly with
      `wasp db migrate-dev --name task_update_kind`.
- [ ] Existing `TaskUpdate` rows migrate to `kind=NOTE`.

### Server

- [ ] `addTaskUpdate({ taskId, body })` exists, is registered in
      `main.wasp.ts`, is auth-protected, and is tenancy-safe.
- [ ] `addTaskUpdate` trims body and rejects empty notes.
- [ ] `addTaskUpdate` creates `TaskUpdate(kind=NOTE)`.
- [ ] `completeTaskFromFocus({ taskId })` exists, is registered in
      `main.wasp.ts`, is auth-protected, and is tenancy-safe.
- [ ] `completeTaskFromFocus` requires `startedAt != null`.
- [ ] `completeTaskFromFocus` is idempotent for already-done tasks: it returns
      the existing completed result and does not write a second `COMPLETED`
      update.
- [ ] `completeTaskFromFocus` sets `isDone=true`, stamps `completedAt`, clears
      `startedAt`, and creates one `TaskUpdate(kind=COMPLETED)` in a single
      transaction.

### UI

- [ ] Focus mode renders task updates as a chronological activity thread.
- [ ] Focus mode distinguishes user notes from completion system events.
- [ ] Focus mode includes a note composer.
- [ ] Submitting a non-empty note appends it and refreshes the thread.
- [ ] Empty note submit is blocked client-side and server-side.
- [ ] The Focus Complete button uses `completeTaskFromFocus`.
- [ ] Completing from Focus removes the task from active focus/list surfaces and
      makes it appear in Done today via existing `completedAt` behavior.

### Tests And Verification

- [ ] Unit test: `addTaskUpdate` creates a `NOTE` row and rejects cross-user
      task ids.
- [ ] Unit test: `addTaskUpdate` rejects empty/whitespace body.
- [ ] Unit test: `completeTaskFromFocus` writes task completion fields and one
      `COMPLETED` row.
- [ ] Unit test: `completeTaskFromFocus` rejects an unstarted task.
- [ ] Unit test: duplicate complete does not create duplicate completion rows.
- [ ] UI test or e2e: start a task, add a note in focus, see it in the thread.
- [ ] UI test or e2e: start a task, complete it in focus, see it leave active
      work and appear in Done today.
- [ ] `wasp compile` passes.

## Non-goals

- No `/do` + `/do/today` route merge.
- No removal of completion circles from lists.
- No Not Doing action.
- No task archive fields.
- No Logbook recovery for tasks.
- No `STARTED` or `PAUSED` system events.
- No editing or deleting existing notes.
- No markdown editor; plain textarea is enough.
- No comments, mentions, reactions, attachments, or notifications.
- No CLI commands.
